# M0: what TikTok's web app actually does

Observed **2026-09-24** on `www.tiktok.com` in a signed-in Chrome 153 session (one real account: 263 favorites declared, 5 collections shown). Everything here was read from the page's own network responses. Nothing was called by us, clicked to change, or written.

**Confidence labels:** **[observed]** seen directly · **[inferred]** consistent with what was seen but not proven · **[unverified]** not tested. TikTok changes without notice; treat every field name below as "true on this date".

## 0. How this was gathered (and what was deliberately not kept)

- A **passive recorder** wrapped `fetch`/`XHR` in one tab of my own, recording only *endpoint path, query-parameter names (never values), status, and response body* for `/api/*` calls. No cookies, no tokens, no request headers. (My first recorder version kept full URLs in page memory; I reloaded the tab to discard it and used the names-only version.)
- I drove the UI read-only: Profile → Favorites → Posts / Collections → opened one collection → scrolled the favorites list to its end.
- The recorder also saw `/api/post/item_list/`, `/api/repost/item_list/`, `/api/user/playlist/`, `/api/story/item_list/`, `/api/user/list/`, `/api/drama/favorite/drama_list/`. Those are your uploads, reposts and unrelated tabs. **I did not read them**, and the capture rules (§6) must never forward them.
- **No raw captures are committed.** They contain a real person's saved videos, authors and signed URLs. `src/platforms/tiktok/fixtures/*.json` are **reconstructed**: real field names, types, nesting, optional-field patterns and pagination quirks, with entirely synthetic values, generated by `scripts/make-tiktok-fixtures.mjs`. (I first tried scrubbing real payloads in-page; the browser tool's output filter cut the results off, and a leak audit of my own scrubber found it passing real values through, so I dropped that approach rather than ship something I couldn't fully verify.)

## 1. The four endpoints that matter **[observed]**

All under `https://www.tiktok.com`, all `fetch` calls returning JSON with `statusCode: 0` on success. (HTTP methods were not recorded; the extension never issues these calls itself, so it does not matter.)

| Endpoint | What it returns | Interesting query parameters (names only) |
|---|---|---|
| `/api/user/collection_list/` | The user's collections | `count, cursor, secUid, publicOnly, needPinnedItemIds, post_item_list_request_type, video_encoding` |
| `/api/user/collect/item_list/` | **All favorites** (the "Posts" sub-tab), newest saved first | `count, cursor, secUid, needPinnedItemIds, post_item_list_request_type, video_encoding` |
| `/api/collection/detail/` | One collection's header | `collectionId, scene` |
| `/api/collection/item_list/` | Videos in one collection | `collectionId, count, cursor, sourceType` |

Each request also carries ~30 device/browser/session parameters (`device_id`, `odinId`, `verifyFp`, `browser_*`, `screen_*`, `tz_name`, `WebIdLastTime`, `clientABVersions`, …) and possibly signature parameters that I did not enumerate. **Replaying these calls from an extension is not viable**, which confirms the passive-capture design.

Sizes: a favorites page is 385 to 403 KB for 15 items; a collection page of 28 items was 737 KB. The capture path must stream/chunk large bodies.

## 2. Response shapes **[observed]**

```
collection_list  { collectionList[]: { collectionId, name, status, total("48"), userId, userName, cover.urlList[] },
                   cursor:"6", hasMore:false, total:6, extra:{now,logid,…}, statusCode, status_msg }
collection_detail{ collectionInfo:{ collectionId, name, status, total, userId, userName, cover }, … }
item_list (both) { itemList[]: <item>, cursor:string, hasMore:boolean, total?:number, extra, log_pb, statusCode }
```

**Item** (identical in both list endpoints except 3 optional fields present only on favorites: `creatorAIComment`, `effectStickers`, `aigcLabelType`):

| Purpose | Field | Notes |
|---|---|---|
| id | `id` (string, 19 digits) | |
| caption | `desc` | up to **2,980 chars** seen; empty in 5/227 |
| hashtags | `challenges[].title`; `textExtra[]` where `type === 1` (`hashtagName`, `start`, `end`) | `challenges` is absent on 34/227 items (15%). Max 32 per item. `textExtra` entries with `type === 0` (41 seen) are probably @mentions **[inferred]** |
| author | `author.uniqueId` (handle), `author.nickname`, `author.id`, `author.secUid`, `author.verified` | canonical URL = `https://www.tiktok.com/@{uniqueId}/video/{id}` |
| sound | `music.title`, `music.authorName`, `music.original`, `music.id` | |
| posted | `createTime` (epoch **seconds**) | |
| stats | `stats.{playCount,diggCount,commentCount,shareCount,collectCount}` (numbers) and `statsV2` (same as **strings**, plus `repostCount`) | |
| duration | `video.duration` (seconds) | **0 for photo posts** |
| thumbnail | `video.cover` (URL) | present on 227/227, including photo posts |
| language | `textLanguage` (`en`, `un` = undetermined for 36/227, and a few others) | |
| flags | `collected` (true for all), `privateItem`, `secret`, `isAd` (**14/227 saved items are ads**), `isReviewing`, `isProhibited` | |

**Photo carousels are 22% of the sample (49/227).** They carry `imagePost: { cover, images[], shareCover, title }`, `poi`, `titleLanguage`, `playlistId`, and `video.duration = 0`. `imagePost.title` is empty for 18/49. The parser must treat "no duration" as "photo", not "missing".

Optional keys and how often they were present (of 227): `challenges` 193, `textExtra` 197, `contents` 222, `duetEnabled` 146, `stitchEnabled` 146, `diversificationId` 169, `penaltyContext` 178, `videoSuggestWordsList` 130, `stickersOnItem` 82, `effectStickers` 56, `poi` 49, `imagePost` 49, `anchors` 26, `adAuthorization` 10. **The parser must treat everything except `id` as optional.**

## 3. Pagination **[observed]**, and the surprises

| List | `cursor` means | Page size | End of list |
|---|---|---|---|
| Favorites (`collect/item_list`) | **Unix time in seconds, strictly decreasing** (e.g. Jun 2026 → Apr 2026 → … → Feb 2024) | 7 to 15 items (request asked for 15) | `hasMore: false` **and `cursor: "0"`** |
| Collection items (`collection/item_list`) | **Offset** (`"30"`, then `"48"`) with `count` = 30 | 28, then 17 | `hasMore: false` |
| Collection list | offset-like (`"6"`) | all in one page | `hasMore: false` |

**Surprises the extension must be built around:**

1. **Declared totals are wrong. Completion is `hasMore === false`, never `count === total`.** The favorites tab declared 263 but delivered **227 unique videos** (36 silently missing, ~14%); the collection said 48 and delivered 45; `collection_list` said `total: 6` and delivered 5 (the UI also shows 5 cards though its tab label says 6; **why is unresolved** [unverified]). Pages are shorter than requested because unavailable videos are dropped without a marker. *Store `declared_total` and `items_seen` separately and show "N videos unavailable".*
2. **Collections are a subset of favorites.** All 45 collection items were present in the flat favorites list [observed for this account; other accounts unverified]. Only ~97 of 263 favorites are in any collection, so ~2/3 of what a user has saved is **uncollected**.
3. **There is no per-video saved-at field**, but the favorites cursor is a saved-time boundary [inferred]: it decreases page by page, is unrelated to the videos' posted dates, and the first page's cursor (Jun 2026) is months before "now" (Sep 2026), consistent with "the save time of the last item on this page". So `saved_at` can be **estimated per page** (bounded above by the previous page's cursor, below by this page's), with page granularity of 7 to 15 videos, i.e. anywhere from days to months in sparse periods. Collections give order only, no time. *This answers the open question in `STORAGE_SPIKE.md` §3.5: derive `saved_at` from the favorites list, join collection items on `id`, and label it `interpolated`; after the first import, `first_seen_at` (the sync that first sees a video) is accurate to the sync interval.*
4. **Re-opening the Favorites tab re-fetches the first pages** (identical cursor and first id): 19 responses were captured for 17 distinct pages. **De-duplicate by `(cursor, first item id)`**, and use `id` as the idempotency key.
5. **Thumbnails expire in ~2 days.** All 257 captured `video.cover` URLs carried an `x-expires` parameter about **47 hours** ahead. Stored thumbnail URLs are stale within 2 days, so the UI must tolerate dead thumbnails, and every passive capture should refresh `thumbnail_url`. *(Confirms the brief's §5.4.)*

## 4. Getting data out of the page: what works **[observed]**

- **No collection data is in the initial HTML.** The hydration blob (`__UNIVERSAL_DATA_FOR_REHYDRATION__`, ~266 KB) holds `webapp.app-context`, `webapp.user-detail`, `webapp.biz-context`, etc., but no favorites or collections. Everything arrives through the four endpoints above, so `fetch`/`XHR` interception is sufficient and the hydration blob only needs to be read for identity.
- **Identity guard:** `webapp.app-context.user.{uniqueId, uid, secUid}` identifies the signed-in user; compare `uniqueId` with the profile being synced and refuse to proceed on mismatch (the brief's "own data only" rule).
- **Cold navigation shows a "Please wait…" interstitial for ~5 to 10 s** before the real page replaces it (twice observed). Content scripts run on both documents; the capture hook must be (re)installed on the final one and must not treat the interstitial as the app.

## 5. Driving the list: **the sync tab must be visible** **[observed]**

The lists paginate by infinite scroll. In this session the automation tab reported `document.visibilityState === "hidden"`, and:

- `window.scrollTo(...)` and `window.scrollBy(...)` **did not move the page** and loaded **no** further pages (steps recorded: scrollY frozen);
- the End key did nothing;
- **real wheel events (10 ticks each) did load pages, roughly one page per scroll**: 14 scrolls took the list from 4 to 19 captured responses and to the end (`hasMore=false`).

So in a hidden/occluded tab the page's own lazy loading is throttled and programmatic scrolling silently stalls. **M4's sync driver must open the sync tab active and in a focused window and tell the user to leave it visible**, and it must detect "no new page after N steps" rather than loop forever. *Whether programmatic scrolling works in a visible tab is [unverified]; M4 must test it and fall back to synthetic wheel events if not.*

## 6. Proposed capture rules for the TikTok adapter

Forward only responses whose path is exactly one of: `/api/user/collection_list/`, `/api/user/collect/item_list/`, `/api/collection/detail/`, `/api/collection/item_list/`. Drop everything else in the MAIN-world hook before it ever reaches the isolated world (uploads, reposts, playlists, stories and other tabs are out of scope and more private than what the user asked us to index).

## 7. Things I did **not** verify

- The `count` values TikTok sends (recorder stored names only). Offset step 30 and page size 15 are inferred from the responses.
- Why `collection_list.total` is 6 while 5 collections exist (private/hidden collection? `publicOnly` param?). Also the meaning of collection `status` (one collection had `status: 0`).
- Whether a collection's item order is save order (needed for `position` to mean "recently saved").
- Cursor semantics for a *brand-new* save (does it appear on page 1 with a cursor near "now"?). M3's live smoke should save one video and diff.
- Behaviour for accounts with private collections, or thousands of favorites (rate limiting, captchas).
- Photo-carousel handling of `music` and `stats` beyond presence.
