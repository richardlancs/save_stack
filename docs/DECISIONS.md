# Decisions

One line of "why" per decision. Newest at the bottom of each section. Status: **proposed** until the milestone that owns it is accepted.

## Tooling (M0)

| Decision | Why |
|---|---|
| **WXT 0.21 (Vite 8)** builds the MV3 extension, with `srcDir: 'src'` and `entrypointsDir: 'extension/entrypoints'`. | Matches the brief's repo layout; handles offscreen page, MAIN-world scripts and side panel entrypoints; WASM asset emission worked first try. |
| **Tests load the extension in Playwright's bundled Chromium, not branded Chrome.** | Branded Chrome 137+ ignores `--load-extension`. Chromium 153 (Chrome for Testing family) honours it and runs extensions headless. |
| **TypeScript 7 needs `"types": ["chrome"]` in `tsconfig.json`.** | TS 6+ no longer auto-includes `@types/*`; without it the `chrome` global is undefined. |
| **`content_security_policy.extension_pages` = `script-src 'self' 'wasm-unsafe-eval'; object-src 'self'`.** | MV3's default CSP blocks `WebAssembly.instantiate` (hit in the first spike run). `wasm-unsafe-eval` permits compiling `.wasm` only. It does not allow JS `eval`, inline scripts or remote code. |
| **`@sqlite.org/sqlite-wasm` 3.53.4 with the `opfs-sahpool` VFS.** | No COOP/COEP or SharedArrayBuffer requirement, so no extra manifest headers. FTS5, DBSTAT and math functions are compiled in. The wasm is 869 KB. |
| **Storage tests in Node use the package's Node build (`dist/node.mjs`) with in-memory DBs.** | Lets the storage contract suite run under Vitest against the real engine, without a browser. |

## Storage (M0 spike; **accepted 2026-09-24**, evidence in `STORAGE_SPIKE.md`)

| Decision | Why |
|---|---|
| **SQLite-WASM (`opfs-sahpool`) + FTS5 behind `StorageAdapter`; IndexedDB fallback not needed.** | Whole path (SW → offscreen → Worker → OPFS → FTS5) works in a real MV3 extension: 50k rows, persistence across worker restart, `quick_check` ok, ~120 ms cold start. |
| **Exactly one DB owner: a singleton offscreen document + one dedicated Worker.** | The pool is exclusive; a second installer is refused in ~40 ms. On startup the owner retries install with a short bounded backoff. |
| **Safe pragmas only:** default page size, `journal_mode=TRUNCATE`, `synchronous=NORMAL`, `temp_store=MEMORY`, `cache_size≈-32768`. | Six variants were within noise of each other (2.5k to 2.8k items/s), so exotic settings buy nothing. `journal_mode=MEMORY/OFF` risks corruption on a crash for no gain. |
| **Drop the trigram table; use a `LIKE` substring fallback for CJK/emoji chips and edit-distance for did-you-mean.** | Trigram cost ~20% of DB size and ~30% of ingest speed, and can't match 2-char CJK or emoji. `LIKE` did all of it: 2 to 3 ms first page, ~20 ms count at 50k. |
| **Drop `items.url`; make `raw_json` opt-in.** | ~1.9 KB to ~1.2 KB per item (≈ 60 MB at 50k instead of 97 MB). URL is derivable via `adapter.canonicalUrl`. |
| **Tiered search: own-word matches first, related-only matches via FTS5 `(full) NOT (direct)` only to fill the page; total capped at 10,001.** | The single-pass pipeline hit 266 to 479 ms for multi-chip ANY searches. Tiered runs at 34 to 73 ms p95 in the worst case and ≤ 35 ms for most searches. |
| **Per-chip counts and per-row "why matched" leave the first-paint path** (follow-up call; lazy per-row `explain`). | In SQL they cost ~1 ms per (row, chip) for broad chips: 130 to 290 ms for a 30-row page. |
| **Multiword chips also try the concatenated hashtag** (`meal prep` → `mealprep`). | Hashtags are one token; without this "meal prep" matched 0 videos in the benchmark, with it 3,183. |

## TikTok ingestion (M0 findings; evidence in `TIKTOK_FINDINGS.md`)

Status: **sync scope accepted** (all favorites + collections as tags); the rest are **proposed** until M3/M4 verify them live.

| Decision | Why |
|---|---|
| **Capture only four endpoints:** `/api/user/collection_list/`, `/api/user/collect/item_list/`, `/api/collection/detail/`, `/api/collection/item_list/`. Drop everything else in the MAIN-world hook. | Those carry all the data. The other `/api/*` calls on the page are the user's own uploads/reposts, which are out of scope and more private. |
| **Sync the flat favorites list as the base set; treat collections as membership tags.** | Collections are a subset of favorites (45/45); ~2/3 of saves are in no collection; the favorites cursor is the only saved-time signal. |
| **Never trust declared totals. Completion = `hasMore === false`.** Store `declared_total` and `items_seen` separately. | 263 declared vs 227 delivered; 48 vs 45; `collection_list.total` 6 vs 5 delivered. |
| **`saved_at` is estimated from favorites cursors and labeled `interpolated`;** later syncs use `first_seen_at`. | No per-video saved time exists; cursors are saved-time page boundaries (inferred). |
| **De-duplicate re-fetched pages by `(cursor, first id)`; upsert by `(platform, external_id)`.** | Re-opening the tab re-requests the first pages. |
| **Sync tab must be visible (active tab, focused window).** | In a hidden tab, programmatic scrolling and lazy loading silently stall; real wheel events worked. |
| **Refuse to sync unless the profile's `uniqueId` equals `webapp.app-context.user.uniqueId`.** | Enforces "only the signed-in user's own data". |
| **Parser treats every field except `id` as optional; photo posts (22%) have `duration = 0` and `imagePost`.** | Observed optional-field rates 0.2 to 87%. |
| **Fixtures are reconstructed from observed structure, not raw captures.** | Raw captures contain a real person's saved videos and signed URLs; my in-page scrubber failed its own leak audit, so it was not used. |

## M1: storage + RPC (implemented; evidence in the tests and `bench/`)

| Decision | Why |
|---|---|
| **Four M0 decisions accepted (2026-09-24):** sync all favorites + collections as tags; slim schema; split search API (results / `getChipInfo` / `explainMatch`); recency order + "narrow it" prompt above 10,000 matches (implemented in M2). | Evidence in `STORAGE_SPIKE.md` §3 to §4. |
| **Migrations are TypeScript string modules, not `.sql` files loaded with `?raw`.** Applied in order under `PRAGMA user_version`, each in its own transaction with the version bump; a newer database is refused. | Loads identically under Vite, Vitest and plain Node (`tsx` benches). Tested: idempotent, contiguous, atomic on failure, upgrade keeps data. |
| **`StorageAdapter` is async and excludes search until M2.** The SQLite adapter takes any sqlite-wasm `Database`. | Keeps an IndexedDB fallback possible; one implementation runs in Node tests and in the OPFS worker. |
| **Two columns added to the M0 schema:** `media_type` ('video' or 'photo') and `is_ad`. | Findings: 22% of favorites are photo carousels (`duration = 0`), and 14/227 saved items were ads. |
| **`saved_at` provenance: exact > first_seen > interpolated > unknown.** Set at insert, replaced only by a strictly better source, never downgraded. | TikTok exposes no per-video saved time; the sync layer labels what it estimated. Tested. |
| **Full-text rows are written after memberships**, so the `collections` column is correct first time; membership changes and collection renames refresh only the affected rows. | Chips match collection names ("recipes" finds a video in the Recipes collection). A test asserts the index mirrors the tables after every kind of change, and mutation checks confirmed those tests fail when the maintenance is removed. |
| **`reconcile` refuses an empty seen-list unless `allowEmpty`.** Missing videos become `available = 0`, never deleted. | A failed or interrupted sync must not silently mark the whole library unavailable. |
| **A rolled-back batch clears the in-memory hashtag id cache.** | A mutation check showed that without it a failed batch poisons later ones (dangling ids). |
| **RPC envelope v1** `{v, id, method, params}` -> `{v, id, ok, result \| error, serverMs?}`; all methods idempotent so the service worker can safely retry. The DB worker handles **one request at a time**. | A wipe must never interleave with another call. `serverMs` separates database time from transport time. |
| **Test hooks exist only in a build made with `WXT_E2E_HOOKS=1`, which is emitted to `.output-e2e/`.** A normal build contains no hook (verified by grep). | The e2e needs a way to drive the service worker; it must never ship. |
| **Bench/e2e scripts run with `tsx`; Node types are pulled in per file** with `/// <reference types="node" />`. | Keeps Node globals out of extension code. |
| **The M0 spike wiring was removed from the production entrypoints.** It stays reproducible at git tag `m0-spike`; `bench/spike-core.ts` remains as the reference for M2's search shapes. | One code path in production. |

Measured on the real extension (Chromium 153, real OPFS, 50k synthetic videos): **ingest 4,811 items/s** through service worker -> offscreen -> worker (budget 2,000); 5,762 items/s inside the worker alone; 2,291 items/s including my Playwright harness's own transfer overhead, which is not part of the product. 60 MB database; cold start about 1.1 s including launching the browser; recovery after the offscreen document is destroyed 180 ms; data survives a full browser restart.

## M2: search (implemented; evidence in `tests/search/`, `docs/SEARCH_PERFORMANCE.md`)

| Decision | Why |
|---|---|
| **Search is three calls: `search` (results + capped total + suggested chips), `getChipInfo` (per-chip counts, related terms, did-you-mean), `explainMatch` (why one result matched).** | Keeps first paint fast; per-row attribution in SQL cost 130 to 290 ms. |
| **Two ranking tiers:** videos matching the chips' own words first (bm25 with weights hashtags 4, caption 2, author 1.5, sound 1, collections 0.5), then related-only matches via FTS5 `(full) NOT (direct)`, queried only to fill the page. | The single-pass version measured 266 to 479 ms for multi-chip ANY searches. |
| **Related terms are data (`related-terms.json`: 87 categories, 167 aliases, ≤ 30 terms each), behind a `TermExpander` interface.** | Editable without code; replaceable by embeddings later. Measured: `"food"` alone finds 17% of the hand-labeled food videos, with related terms 100%. |
| **A query shares a total budget of 60 related terms across its chips** (1 to 2 chips keep 30 each; 5 chips get 12 each; floor 8). `getChipInfo` uses the same share. | Full-text cost grows with expression size (~120 OR'd terms took 60+ ms). Bounds latency by construction; costs a little recall on many-chip queries. |
| **More than 10,000 matches = "too broad": total capped at 10,001, relevance skipped, newest-saved first.** When the chips' own words alone exceed 10,000, only those matches are listed. | The M0 mitigation, now measured: broad ANY 70 → 43 ms and 93 → 49 ms. Related-only matches are not in a too-broad listing (documented in `UI_CONTRACT.md`). |
| **Chips with CJK/emoji match by substring over the plain `items` table** (five columns + hashtag/collection ids resolved first); such searches are ordered newest-saved. | FTS5 cannot serve them. **Over the 50 ms budget** (66/60/90 ms p95): documented exceptions with a 120 ms ceiling; fix options are in `SEARCH_PERFORMANCE.md`. |
| **Cursors are self-describing, carry the total, and are tied to their sort** (`r:<offset>:<total>`, `k:<sort>:<value>:<id>:<total>`, and `d:` for an own-words listing); column-ordered pages use keyset pagination; the total is clamped. | Later pages skip the count (71 → 31 ms), stay stable if rows arrive between pages, and a cursor replayed under another sort is refused instead of silently skipping rows (found by code review). |
| **`SUPERSEDED` error and a search gate that yields one event-loop turn before a search.** | Found by the real-extension e2e: while the worker is busy, later messages cannot register, so a stale queued search still ran. |
| **Suggested chips exclude platform-noise hashtags (`fyp`, `foryou`, `viral`, ...) and chips already in use; only the first page carries them.** | Noise would otherwise dominate the suggestions. |
| **Snippets are structured segments computed with a lightweight JS matcher, never HTML.** Which chip matched a result is answered authoritatively by `explainMatch` (SQL). | Captions are untrusted; the highlighter is an approximation for display only. |
| **The quality bar is a hand-labeled library:** recall ≥ 90% and precision ≥ 85% overall (measured 96.3% / 90.8%), per category recall ≥ 70%. | Related terms are a judgment call; a labeled set catches gross errors. The traps ("cooking up a surprise") count as unavoidable false positives. |

## M3: TikTok adapter + passive capture (implemented; evidence in `tests/platforms/`, `tests/capture/`, `e2e/capture.ts`)

| Decision | Why |
|---|---|
| **The platform contract is `PlatformAdapter`** (`src/platforms/types.ts`): `id`, `parserVersion`, `hostMatches`, exact-path `captureRules`, a **pure, total** `parse`, and `canonicalUrl`. The pipeline, hook, relay and router know nothing about TikTok; adding a platform means writing an adapter and listing it in `registry.ts`. | The brief's "start with TikTok, expand later". |
| **Capture reads only four exact paths** (`/api/user/collect/item_list/`, `/api/collection/item_list/`, `/api/user/collection_list/`, `/api/collection/detail/`) on `https://www.tiktok.com`. Everything else the page requests (uploads, reposts, stories, playlists) is never read, cloned or forwarded. | Privacy: those are more private than what was asked for. Enforced in the in-page hook itself and again at both later stages; tested with look-alike hosts, prefixes and suffixes, and mutation-checked. |
| **Only two request values ever leave the page: `cursor` (digits, at most 16) and `collectionId` (digits, at most 24).** No headers, cookies, tokens, other query values or request bodies. | The mock page's requests carry secret-looking params and headers; the e2e asserts no message the page can observe contains any of them. |
| **Three content scripts.** A MAIN-world hook (3.5 KB, no extension API, no database code, no `eval`), an isolated relay, and (M4) the isolated sync page driver. The hook wraps `fetch`/XHR in Proxies over the originals (same name/length/prototype/toString) and returns a derived promise, so the page sees the same values and a rejection is unhandled exactly as without us; a reused XHR object can never report a later request under an earlier one's kind. WXT's default announcement of isolated scripts (`window.postMessage` with the extension id) is switched off and the build check verifies it. | Only the page's own world can see its responses; the hook must change nothing the page can observe. |
| **No `host_permissions`.** Content scripts are declared with `matches`, which needs none; the extension never fetches anything itself. Permissions are now `offscreen`, `unlimitedStorage`, `storage` (capture counters and, in M4, resumable sync state). | Least privilege; verified from the built manifest on every gate. |
| **Trust model, stated plainly: the hook runs in the page's world, so any script on tiktok.com could post a message shaped like ours.** A nonce cannot help (it would sit in the same page-readable world). Defense is limits, not secrecy: validation at the relay AND again in the service worker, kind allowlist, digits-only request values, a body size cap, a clock-skew check, the identity guard, and that capture can only add or refresh saved-video rows (never delete, read or export). A forged message is refused if it fails any of those; one that passes them is indistinguishable from a real page and can only add or refresh rows for the signed-in user's own account. | Documented in `capture-protocol.ts`; a forged-message e2e proves the refusals. |
| **Identity guard: only the signed-in user's own data.** A capture needs the signed-in user (hydration blob `webapp.app-context.user.uniqueId`) AND a page URL showing that same user's profile; a payload that names another account (collection lists/details) is refused. Handles compare case-insensitively. | The brief's "own data only" rule; tested for other people's collection pages, signed-out pages and payload owner mismatch. |
| **The library is bound to ONE account per platform, and the binding lives in the DATABASE** (`meta` table, schema v2), written in the same transaction as the data it protects (`ParsedBatch.account`; a different account raises `AccountMismatchError` and the batch writes nothing). Wipe clears it, export carries it, import restores it. The binding is by the platform's stable user id when the page has one (`webapp.app-context.user.uid`), else by handle, so a username change is followed and someone who takes the old name is refused. | The M3 review showed a binding kept in `chrome.storage.local` fails open (a read error, a kill between the write and the binding, a wipe racing a capture). The pipeline keeps a status cache only for a cheap early refusal and for display. A forged first message can still pin the binding to a bogus account: that needs a script running on tiktok.com itself, and the cost is a wipe; documented, not defended. |
| **Body parsing happens in the service worker, not the page.** The hook forwards JSON text. | A hostile body can then only hurt one worker call. |
| **There is no duplicate suppression: every page is applied.** A page that held videos but added none is REPORTED as a duplicate (`duplicate: true`, counted in `duplicates`), not skipped. | The M3 review showed fingerprints of the response text cannot recognise a re-fetched page on the real site (per-response envelope fields, re-signed thumbnail URLs), and skipping would also skip the thumbnail/stat refresh a re-fetch is good for. Re-applying a page is idempotent and takes ~10 ms. Tested: a re-sent page with new envelope fields and a re-signed cover URL changes the thumbnail and adds nothing. |
| **Captures are processed strictly one at a time, in arrival order.** The cheap checks (sender, shape, page handle, cached account) run before the body is parsed; status writes are coalesced (one in flight, newest wins). | A flood of refused messages must cost almost nothing. Tested: a slow earlier store cannot be overtaken; 300 refused messages never write the status concurrently, and never parse a body. |
| **`saved_at` for favorites is estimated, and labelled honestly.** Pages with both cursor bounds are interpolated (`interpolated`); the last/only page has no lower bound, so its times only preserve ORDER and are labelled `unknown`; cursors in the future are never trusted. NEW saves at the head of the list in an already-populated library are dated by first sight (`first_seen`, capture time, newest first, 1 s apart; `ParsedBatch.headOfList`). | TikTok exposes no per-video save time. The sync e2e proved an interpolated date for a new save can sort BELOW older videos (page boundaries shift as the list grows), so new saves use first sight; precision is the sync interval. Verified: newest-saved order equals the platform's list order after the first import and after an incremental sync. |
| **Parser is hand-written and total, not schema-driven.** (The prompt suggested valibot.) Every field except the video id is optional; a field a record does not provide stays `undefined` and storage KEEPS what it already holds (an explicit empty caption replaces; a stub never blanks). Hard caps: 300 items per page, 500 collections per list, captions 10,000, hashtags 64, unknown keys 64 characters. A response that leaves its list out but says `hasMore: false` with no error is an empty page. A seeded fuzzer (6,000 mutated real-shaped payloads) asserts the output is always storable. | A schema library adds a dependency and a failure mode for data that is 87% optional. The M3 review showed a partial record blanked stored text and that one message could insert 200,000 rows: both fixed with regression tests. |
| **Completion is `hasMore === false`, never a count.** Declared totals are stored separately; the e2e's collections declare 21/19/0/48 and deliver 19/18/0/46. | Observed: 263 declared vs 227 delivered. |
| **`getCaptureStatus` is answered by the service worker, and database RPC is refused for any sender that is not one of our own extension pages** (a content script in a web page cannot reach export/wipe/import). | Defense in depth for the trust model above; unit-tested in `tests/capture/router.test.ts`. |
| **Drift is reported, not guessed at:** unknown item keys, missing-field counts and dropped records accumulate in the capture status (M6 shows a banner). | The platform will change without notice. |
| **The mock TikTok** (`e2e/mock-tiktok.ts`) serves a hydration blob, scroll-paginated pages that fetch the four endpoints with noisy secret-looking params, blocked endpoints, a "Please wait" interstitial, unavailable videos, photo carousels and a stranger's collection. It uses the same payload builders as the parser tests. The user's real account is never touched. | Repeatable and safe; the live behaviour is checked separately by `docs/LIVE_CHECKLIST.md` (M6). |
| **The offscreen document ignores runtime messages from anything but our own service worker** (`sender.id` is ours and there is no `sender.tab`); the router refuses database RPC from non-extension origins. | Runtime messages reach every extension context, so the router's guard alone could be bypassed by a content script addressing the offscreen document directly (M3 review). |
| **Memberships that arrive before their collection exists are kept in memory and applied when the collection list or detail arrives** (`skippedMemberships` is counted). | The real site does not promise the collection list beats the item list; the mock does, so the e2e could not have shown the loss. |
| **The end-to-end runs are hermetic.** The mock is a local HTTPS server for `www.tiktok.com`; the test browser resolves that name to it and every other host to nothing (`--host-resolver-rules`), and each run first proves the real internet is unreachable. | Found the hard way: a window opened by the extension itself bypassed Playwright's request interception and loaded the REAL site (anonymously, from a temporary profile with no login and no account involved; three page loads while debugging). It cannot happen again. |

## M4: sync (implemented; evidence in `tests/sync/`, `e2e/sync.ts`)

| Decision | Why |
|---|---|
| **Sync is a pure state machine** (`core/sync/machine.ts`): a reducer `(state, event) -> (state, effects)` with no I/O, no clock and no platform names. The service worker persists the state BEFORE performing effects and feeds events from three sources: the capture pipeline (pages and refusals), the page driver (ready, hidden, visible, stalled, blocked) and the browser (tab closed, heartbeat alarm). | A killed service worker resumes exactly where the state says; every transition is unit-testable (97 tests, incl. 300 random-event runs asserting invariants). |
| **User-initiated only, in a dedicated, focused window.** `chrome.windows.create` and `tabs.update`/`sendMessage` need no permission; the only new permission is `alarms` (a 30 s heartbeat that notices a hung window or a killed worker; no install warning). | Least privilege; hidden or occluded tabs stall programmatic scrolling (findings section 5), so the window must be visible. |
| **The page driver only scrolls and waits.** Every scroll is preceded by a random 0.7 to 1.5 s think-time (the first included), with a longer pause every 8 to 14 steps; it stops the moment the page shows a login wall or challenge, refuses to scroll a hidden window, and reports "stalled" when the list stops growing. Production ignores any pacing override. | Human-like pacing (verified end to end from the server's side: consecutive pages of one list were at least 879 ms apart). |
| **Order: signed-in check, saved list, collection list, each collection.** The saved list is the base set; collections are membership tags on it. An incremental pass stops the saved list after two consecutive pages that added nothing new, but ONLY when a complete pass has run before (otherwise it runs as a full pass and says so); collections are always read completely. | Incremental correctness: a partly filled library must not stop early. Collections are small, and a video newly added to an old collection must be seen. |
| **"Complete" is only claimed for a list whose pages CHAINED** (each request cursor equals the previous response cursor) up to a page with `hasMore === false`. A gap re-reads the list from the top (bounded), then finishes it as `partial` with a warning. Only a complete pass reconciles. | A missed page must never make the library forget a video. |
| **Reconcile** (full mode only): a complete saved pass marks videos not seen `available = 0` (kept, never deleted); a complete collection pass drops memberships not seen. The coordinator refuses when nothing was read, when it saw under half of a library of 20 or more, or when a collection came back empty though the platform declares videos; each refusal is a visible warning. Ids seen are kept in small chunks in `chrome.storage.local` so a killed service worker loses none. Collections are never deleted (the M0 note that a declared 6 listed only 5 collections is unresolved, so an unlisted collection might just be hidden). | The M1 principle: a failed or interrupted sync must not silently empty the library. |
| **Things that need the user stop the sync and say why** (`needs_attention`: not signed in, verification challenge, wrong account, someone else's page, window closed, unreadable responses in a row, a list that never loads, the collection list never arriving). Two clear themselves: a hidden window (when it is visible again) and a list the user opens by hand (pages start arriving; the collection list is remembered while waiting). | Guided fallback for everything unverified against the live site (docs/LIVE_CHECKLIST.md): the sync never fails silently. |
| **The driver clicks the Favorites tab once if it can find it** (best-effort selectors, unverified). If not, the list stalls and the user is asked to open it. | The URL that opens the favorites list on the real site is unverified. |
| **A wipe or import cancels a run in progress FIRST** (and closes its window), then replaces the library. | Otherwise a page still in flight could write into the new library. |
| **Sync state, progress and the last complete pass persist** (`chrome.storage.local`); a `SyncProgressMessage` is broadcast on every change; RPC: `startSync` (BUSY if running), `pauseSync`, `resumeSync`, `cancelSync`, `getSyncStatus`, each returning the state. | The side panel (M5) and any replacement UI only need these. |
| **Only the sync window's own tab moves a run.** Captures from any other tab are still stored (passive capture) but are invisible to the sync: a bystander tab on someone else's profile can no longer stop a run with "wrong page", and a forged message from another tab cannot end a list. The same plausibility guard that protects the saved list (a pass that saw under half of what is stored is refused, each video counted once even if a page was replayed) now protects every collection. | Found by the second code review; the first M4 design let any TikTok tab feed the state machine, which contradicted the trust model. |
| **The sync window record belongs to a browser session** (`chrome.storage.session` id, written with the record). After a browser restart a stored `running` run says "the sync window was closed, press Resume" and opens nothing by itself; Resume opens a fresh window. Closing the sync closes its TAB, not the window. Wipe or import also forgets the last complete pass. | Tab ids start over each session, so a stale id could have pointed at one of the user's own tabs, and an unattended run must never start on its own. |
| **End-to-end coverage against the mock:** first sync at human pace, incremental early stop and new saves on top, full re-sync reconciling removals, wrong account, pause/resume, cancel, wipe during sync, service worker killed mid-sync, hidden window (forced by an e2e-only attribute, because Playwright's headless browser reports every tab as visible; compiled out of production and checked), sign-in wall, verification challenge, list behind a tab (driver clicks it; user opens it), browser restart. | Each scenario exists because the state machine claims it. |

## M5: side panel (implemented; evidence in `tests/ui/`, `tests/architecture.test.ts`, `e2e/panel.ts`, `docs/screenshots/`)

| Decision | Why |
|---|---|
| **A thin, replaceable panel.** Preact (a few KB), no router, no state library, no CSS framework. The state rules live in three pure modules (`ui/state/query.ts`, `results.ts`, `sync-view.ts`); components only render them; `ui/api.ts` is the ONLY file that touches `chrome.*` or the RPC. | A separate developer is building the real UI. Everything worth keeping (the chip rules, the paging rules, the sync wording) is testable without a browser and portable to any framework. |
| **The layering is a test, not a convention** (`tests/architecture.test.ts`): the UI imports no runtime code from `core/` or `platforms/` (types only), `chrome.*` appears only in `ui/api.ts`, no platform is named in UI or core code, nothing is rendered through `innerHTML`/`eval`; core and platforms never touch `window`/`document`/`chrome`; layers point one way; the MAIN-world script stays small and self-contained. | The first draft of the panel imported a runtime constant from core; the test caught it before I noticed. |
| **The search box is exactly the accepted interaction.** Enter or a comma makes a chip; the Search button (or Enter in an empty box) runs it; the chip's x edits only the DRAFT and the panel says "Filters changed. Press Search to update the results."; no chips = browse everything, newest saved first; All / Any toggle; "Include related words" switch. | The product decision from the brief; every clause has an e2e check. |
| **Results are text.** Captions, authors and collection names are set as text nodes; snippets are the structured segments from the search core (`<mark>` for hits); a caption containing `<script>` and `<img onerror>` is in the e2e fixture and nothing executes. Dead thumbnails fall back to a placeholder. "Why this matched" is fetched only when a row is expanded (`explainMatch`). | Captured text is untrusted; the contract says so. |
| **Sync is a card, not a page:** the state machine's state becomes a headline, a detail line, a progress bar and the buttons that make sense (`sync-view.ts`). When it needs the user, it says what to do in plain words; "Full re-sync" is an explicit checkbox. Results and the footer numbers refresh while a sync runs and when it ends. | The user should never have to know the machine exists. |
| **Results are paged, not virtualized** ("Show more" appends the next page; 10 to 100 videos per page, a saved preference). The prompt asked for a virtualized list. | A windowed list is a rendering optimisation the separate UI developer can add on the same contract (`nextCursor` paging is what it needs); the panel's cold open to first result measures 60 to 80 ms against the 300 ms budget without it (`e2e/panel.ts`). Keeping it out keeps the panel small and its behaviour easy to test. |
| **Export, import and wipe live in the footer;** wipe needs a second, deliberate confirmation ("Keep it" changes nothing). The footer shows the library size and, when the parser reports drift, a banner naming the platform (taken from the backend, never hard-coded in the UI). | Wipe is the one destructive operation. |
| **The toolbar button opens the side panel** (`chrome.sidePanel.setPanelBehavior`, permission `sidePanel`); light and dark themes follow the system; every control has an accessible name and result counts are announced (`aria-live`). | Least surprise; accessibility is cheap to do at this size. |
| **Icons are generated** (`scripts/make-icons.mjs`: a small anti-aliased rasteriser plus a PNG encoder on `node:zlib`), committed under `public/icon/`. | No image tooling or binary sources to keep in sync; regenerate with one command. |
| **An e2e-only DOM attribute stands in for "the window is hidden".** Playwright's headless Chromium reports every tab as visible, so the hidden-window scenario is driven by `data-scroganize-e2e-hidden`, which exists only in a build made with `WXT_E2E_HOOKS=1`; `check:build` fails if the production bundle contains it. | The only way to test the real code path; kept out of production mechanically. |
| **The unused SQLite helper chunks (about 245 KB) are deliberately NOT trimmed from the bundle.** They are referenced by URL constructors inside the library and never loaded at runtime. | Removing them means patching a third-party package for no runtime gain; the total (1.5 MB) is far under the 3 MB budget. |

## M6: hardening, preferences, documentation (implemented)

| Decision | Why |
|---|---|
| **Three preferences** (`relatedWords`, `sort`, `pageSize`) behind `getSettings` / `setSettings`, stored by the service worker in `chrome.storage.local`, validated key by key in `core/settings.ts` (unknown keys and invalid values ignored; never throws). | Enough to make the panel feel like it remembers you, small enough that nothing needs a settings page. A stored value from an older or damaged build can never break the panel: it normalises to defaults. |
| **Every result carries `url`, built by the platform adapter** (`canonicalUrl`), and the search service isolates a failing builder: that result loses its link, the search still succeeds. | The UI must never build platform URLs; a parser-side bug must not take search down. |
| **Related terms are reviewable:** `node scripts/related-terms-table.mjs` renders the bundled lexicon (87 categories) as `docs/RELATED_TERMS.md`. | You asked to review it at the end; a table is the easiest thing to review. |
| **CI mirrors the local gate** (`.github/workflows/ci.yml`): typecheck, unit tests, production build + build check, Playwright Chromium end-to-end (hermetic), benchmarks reported but not blocking. It has NOT been run on a GitHub runner (none available here). | Shared runners are too noisy for a hard 50 ms line; correctness gates are blocking. |
| **The mutation runner compares on LF text and writes back with the file's own line endings,** and restores the original bytes after every mutation and on interrupt. | Windows checkouts are CRLF: a multi-line mutation target silently failed to match. |
| **Every permission is justified, and there are no host permissions** (the prompt allowed `https://www.tiktok.com/*`; not needed): `offscreen` hosts the database Worker (OPFS synchronous handles only work in a dedicated Worker, and a service worker cannot spawn one); `unlimitedStorage` lifts the browser's storage quota for a library that can reach hundreds of MB; `storage` keeps capture counters, the resumable sync state and the preferences; `alarms` is the 30 s heartbeat that notices a hung sync window or a killed worker (no install warning); `sidePanel` is the panel. Not requested: `tabs`, `scripting`, `activeTab`, `cookies`, `webRequest`, any host. Content scripts are declared with `matches`, and the sync window is opened with permission-free APIs. `npm run check:build` fails on any other permission. | Least privilege: the install prompt says only what is true. |
| **No Chrome Web Store submission** (your decision): the extension is loaded unpacked from `.output/chrome-mv3`. | Out of scope; see `docs/GETTING_STARTED.md`. |
